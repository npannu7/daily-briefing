## Training a model on spare compute
Laura: So the thread we just left — Songe, the tool that trains your local model while you're away — ends with someone asking for a SETI‑at‑home style system that stitches idle GPUs everywhere into one training run.
Sarah: Right, and that question — can you actually do that — opens the whole distributed‑training can of worms. Which is where we're headed.
Laura: Exactly. The project's own repo, github.com/sous-labs/songe, is clear: today it runs on one machine. Machines without a GPU still serve and record, but they do not train. The distributed dream lives in the comments, not in the code.
Sarah: Okay, let's teach the concept from the ground up. Why is training so much harder to spread across machines than inference?
Laura: Inference, which is just running the model to get an answer, is embarrassingly parallel. You hand a batch of inputs to ten GPUs, each runs the full model independently, done.
Sarah: Training, which is adjusting the model's internal numbers, is different. Every step needs the same model numbers on every device, then all of them must agree on the average direction to change those numbers before anyone updates.
Laura: And that agreement step — the all‑reduce, a step where every computer shares its direction and they all agree on the average — is where the network chokes you.
Sarah: The all‑reduce moves a lot of data — for a large model it can be gigabytes each step.
Laura: Gigabytes per step means minutes on a home link but milliseconds in a data center. That mismatch is the whole problem.
Sarah: So the field invented three ways to cut the traffic. First: data parallelism, where each computer holds a full copy of the model and works on different data.
Laura: Identical copies, different batches. Simple, but you still move the full direction every step.
Sarah: Second: model parallelism, where the model is split across computers so each holds only a piece.
Laura: No single computer holds the whole model, so the all‑reduce only moves the intermediate results at the cut points, not the full direction.
Sarah: But now you've added latency: the second computer can't start until the first finishes its forward pass — computing the answer — and the backward pass — computing how to adjust — flows the other way.
Laura: Which brings us to a third idea: stagger the work like overlapping shifts. While the second computer runs the forward pass on the next batch, the first runs the backward pass on the previous one. You keep every computer busy, but you need small batches and a schedule that avoids idle cycles.
Sarah: Those idle cycles — where a computer waits for its neighbor — get worse the deeper the pipeline.
Laura: Right. And all three schemes assume the computers are similar — same GPU, same speed, same network. The Songe dream is the opposite: laptops, desktops, a spare server in a closet, all different speeds, all coming and going.
Sarah: Heterogeneous and volatile. That's where collecting several small updates locally before sharing becomes a lifeline.
Laura: Instead of updating every tiny batch, you run several tiny batches on one computer, sum their directions in memory, then do one all‑reduce. It's like a work cell that finishes a tray of parts before calling the forklift.
Sarah: Bigger effective batch, fewer network round‑trips. But it doesn't fix the slowest‑computer problem.
Laura: The slowest computer in the waiting point — everyone waits. In a data center you kill it and reschedule. On spare compute, the slowest computer might be your only GPU right now.
Sarah: So you need flexible schemes where a computer pushes its direction when ready and pulls the latest average when it can. But then you're training on out‑of‑date model numbers — consistency gets fuzzy.
Laura: Which is exactly the trust problem the thread hints at. If a computer returns a corrupted update — maliciously or just a random error — how does the cluster know?
Sarah: In a controlled cluster you sign updates, you run checksums, you have a trusted authority. On random spare hardware? The repo's SECURITY.md is the place to look — but the provided README does not describe a distributed security model or gradient verification.
Laura: The repo today has no distributed runtime, no update verification, no churn handling. The quoted wishes — near‑centralized efficiency on heterogeneous idle GPUs, handles node churn without manual intervention, security model prevents corrupted updates — are not backed by the source. They would need to be added.
Sarah: So the independent check: GitHub source reads single‑machine only. No benchmarks on heterogeneous hardware, no churn tests, no threat model for corrupted updates.
Laura: Correct. What does exist is a clean local loop: record interactions, distill lessons into a small add‑on, rehearse old skills, judge the new version against your own conversations, swap only if it's better. That part runs on one GPU, offline, private.
Sarah: And that local loop is actually clever — learning from its own actions with a separate model that checks quality, plus saved examples to remember old skills so you don't lose old knowledge. But it's not distributed.
Laura: Right. The distributed layer is a separate engineering mountain. To climb it you'd need: a way to let each computer collect several updates before sharing, tuned to its speed; a peer‑to‑peer sharing method that handles computers dropping out; saving not just the model but also the optimizer's extra data so a returning computer can resume without starting over; and a lightweight audit — maybe a cryptographic summary of each update piece — so the cluster can verify a contribution after the fact.
Sarah: Saving progress at that level means storing not just the model numbers but also the momentum buffers, learning‑rate schedules, random‑number states. Like saving the entire machine setup, not just the part.
Laura: Exactly. And the audit idea: each computer commits its update piece to a log, the aggregator verifies a sample, and any dispute triggers a recompute on a trusted computer. But none of that is in the code today.
Sarah: So the thread's excitement is real — people want SETI‑at‑home for LLMs — but the engineering gaps are the ones we just walked through: bandwidth, heterogeneity, slowest computers, trust.
Laura: And the manufacturing analogy holds: you can't run a just‑in‑time line with suppliers who show up randomly, deliver parts at random speeds, and might slip you a defective bracket. You need buffers, inspection stations, and a way to rework without stopping the line.
Sarah: Quick recap: training resists distribution because every step needs a global direction average — the all‑reduce. Three classic cuts: data parallelism (parallel lines), model parallelism (split stations), staggered shifts (pipeline). Spare compute adds heterogeneity, churn, and no trusted authority. Local update collection buys fewer round‑trips; saving progress and audit are the missing pieces for an open, volatile cluster. The Songe repo today does the local loop beautifully; the distributed dream is still on the roadmap.
Laura: That's the segment.
