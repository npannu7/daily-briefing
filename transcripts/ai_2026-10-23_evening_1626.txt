## Cutting the wait for a local reasoning model
Sarah: Okay, picture this. You're running a reasoning model locally — Qwen3, four billion parameters — on a six gigabyte GPU. You hit enter, and then you wait. Twelve seconds. Just staring at a blank line while the model "thinks."
Laura: Twelve seconds for first token. That's the prefill — the model reading your prompt — plus the reasoning trace before it even starts the answer.
Sarah: Right. And the whole time you were typing? The GPU sat idle. So this developer — calls the project MAFDET, after an Egyptian cat goddess who struck snakes before they could attack — they thought: what if the model starts working while I'm still typing?
Laura: Feedforward control. You're using the known input trajectory — the user's keystrokes — to start the computation early, instead of waiting for the final setpoint.
Sarah: Exactly. Two tricks. First, "reads ahead." The KV cache — that's the model's working memory, the key-value pairs that represent everything it's processed so far — it follows your cursor live. You type, backspace, paste a paragraph, the cache updates incrementally. So when you finally hit enter, the prefill is done. Bit-for-bit identical to computing from scratch.
Laura: Incremental prefix caching with edit-aware invalidation. That's genuinely clever. Most implementations just toss the cache on any edit and recompute. How do they handle an edit in the middle of a long prompt?
Sarah: They keep everything up to the first changed token, recompute from there. So fixing a typo at the end is cheap. Changing the first word of a long prompt costs more, but it's still your own GPU cycles — not extra waiting.
Laura: Right. The latency budget stays bounded by the edit distance, not the full context. That's a clean quality-check loop: verify the prefix match, only rework the divergent suffix.
Sarah: Second trick: "thinks ahead." The model starts its reasoning trace before you send. Qwen3 only, so far. It writes out its chain-of-thought — the intermediate steps, the "let me think through this" tokens — while you're still composing.
Laura: Speculative prefill. The target model itself runs speculatively, generating candidate reasoning tokens. Then when the real prompt arrives, you verify: does this reasoning still hold? If yes, you keep it. If the user changed a number, you detect the divergence and roll back.
Sarah: The developer said left alone, the model mostly writes "the user hasn't finished typing..." Eighty-six percent off-topic notes. They added a short framing prompt — "collect facts and partial results instead" — dropped that to about twenty percent.
Laura: A commenter pointed out that twenty percent still represents a lot of wasted compute. They asked: do those bad notes actively hurt the final answer, or just get ignored? Did the thread say?
Sarah: Unclear. The developer didn't measure that. They measured: twenty-four word problems typed in real time. Mean wait after enter went from twelve point two seconds to three point two seconds on the four-billion model. All twenty-four still correct.
Laura: That's a four-x speedup on perceived latency. And the fourteen-billion model — which only half fits in VRAM, so it's swapping to system RAM — went from one hundred eight seconds to forty-seven. That's the pain point people actually feel.
Sarah: One commenter said exactly that: the fourteen-billion number is the bigger deal. Another asked: what if I type "twelve," model writes "three times twelve equals thirty-six," then I change it to fifteen? The code names the new words but doesn't explicitly retract the old number. So the reasoning might carry forward the stale value.
Laura: Stale-state propagation. Classic hazard in any feedforward system with speculative execution. You need a dependency tracker — a way to mark which reasoning tokens depend on which prompt tokens — so an edit invalidates the downstream chain. Sounds like MAFDET doesn't have that yet.
Sarah: The developer admitted: "that's where it sometimes answers the version you didn't send." Honest about the limitation.
Laura: Good. Now — speculative decoding usually means a small draft model proposes tokens, a large target model verifies in parallel. Here it's the same model doing both roles, just time-shifted. The "draft" is the early reasoning on the partial prompt. The "verify" is the final pass when the full prompt arrives.
Sarah: And the verification is exact for the prefill part — the KV cache match is bit-for-bit. For the reasoning part, it's heuristic. The model picks up from its own notes, but if the prompt changed, the notes might be wrong.
Laura: So it's not classic speculative decoding with acceptance-rejection sampling. It's more like a manufacturing cell where you start machining the rough shape while the final CAD is still being approved. If the drawing changes, you either adapt the workpiece or scrap it. The "twenty percent off-topic" is your scrap rate.
Sarah: I like that. And the project is open source, Apache two. Desktop app or terminal UI with a live status line showing what the model is doing with your draft. Model catalog estimates VRAM fit and speed within twelve percent of measured. Automatic llama.cpp setup — no PyTorch needed. Windows: download zip, double-click batch file.
Laura: That's a polished developer experience. llama.cpp is the C-plus-plus inference engine — runs models on CPU or GPU without Python overhead. MAFDET wraps it with the KV cache management and the speculative reasoning loop.
Sarah: Independent check: I looked. This exists only on Reddit. No paper, no blog post outside the thread, no third-party benchmark. The twelve-to-three-second claim, the twenty-four-problem test, the eighty-six-to-twenty-percent off-topic drop — all unconfirmed.
Laura: Important to say. The mechanism is plausible — incremental KV caching is real, speculative reasoning on partial prompts is a known idea — but the specific numbers are one developer's report on one GPU.
Sarah: One commenter had the same idea for their own harness: send tool-call context early so the system prompt pre-fills while the user types. Another asked: what if I use text input as a scratchpad, constantly rewriting? Developer said: some work gets thrown away, but less than you'd expect. Cost is extra GPU cycles on your own machine, not extra waiting.
Laura: That's the right tradeoff for local compute. You're not paying per token. You're spending silicon you already own.
Sarah: Someone asked about Polystrata and Strata — those are streaming inference engines for huge models that don't fit in VRAM. Developer said: right kind of target, needs two things — KV cache that reuses common prefix, and raw completions it can continue. llama-server provides both behind an OpenAI-style API. But on a hundred-twenty-five-billion model streamed from SSD, decoding is slow, so thinking ahead covers less while you type. Same as the fourteen-billion result.
Laura: Memory-bandwidth bound. The speculative window — how far ahead you can think — shrinks as decode latency grows. That's a fundamental limit: your feedforward horizon is bounded by the inverse of your throughput.
Sarah: So for Nikhil — this turns a local reasoning model from a batch tool into an interactive one. You type, it thinks, you hit enter, answer appears. The draft-verify pattern... we've seen this before.

## When AI clinical advice costs more than human judgment
Laura: So the other thread I kept open was this retrospective study making the rounds on the science subreddit — the one claiming LLM-recommended care costs substantially more than physician care because the models order more tests and specialist referrals.
Sarah: Wait, really? That's the one where the Reddit post text says every model they tested — general purpose and medical — suggested more diagnostics than the treating physician on the same cases?
Laura: That's the post. The paper's in NEJM AI, but the link throws a four-oh-three, so we couldn't read the primary source ourselves. Everything we have is the Reddit thread and whatever the post quotes from the abstract.
Sarah: Okay, that's wild. And the comments are already fighting about whether "more testing" equals "better care" or just "defensive medicine on steroids."
Laura: Exactly. One physician commenter put it neatly: quality of care times quantity of care equals cost of care. You fix one variable, the others move. Another person argued that if you spent a million dollars per patient you'd get better outcomes at diminishing returns — the tradeoffs aren't easy to evaluate objectively.
Sarah: Right, the "is a ten-thousand-dollar test worth it if it saves a small fraction of lives" question. And then the insurance comparison shows up — someone asking what's the difference between this study's LLMs and UnitedHealthcare's denial bot.
Laura: Different objective functions, as one commenter said. The study models were prompted to diagnose and treat. Insurance models are optimized to deny. Same architecture, opposite loss functions.
Sarah: Loss function — that's the mathematical score the model tries to minimize during training. Think of it like a cost function in optimal control: you define what "error" looks like, and the optimizer pushes the system toward zero error. Change the cost function from "missed diagnosis" to "unnecessary payout," and the controller drives a completely different trajectory.
Laura: Good analogy. And that connects to what we discussed Thursday — the sleep-ECG model as an algorithmic medical device. There the cost function was clinical risk prediction. Here it's "be thorough." The comment thread even flags that successive model generations haven't curbed the over-ordering. Capability increases, but the thoroughness stays.
Sarah: Thoroughness as a feature, not a bug. Like a consultant who orders the full panel because the liability of missing something outweighs the cost of the tests. But in a system that can't afford full workups on everyone, that's a failure mode — over-cautious generation.
Laura: That's the hallucination-adjacent framing the post uses. Not fabricating facts, but generating excessive differential diagnoses and workup plans. In control terms, it's a controller with high gain on the "sensitivity" knob and no integral action to penalize resource consumption.
Sarah: High proportional gain, no integral term to accumulate cost penalty. The output saturates at "order everything."
Laura: Precisely. And the study design — retrospective clinic notes — means we're comparing LLM suggestions on historical cases against what the physician actually did. That's not a randomized trial. It's a bench test on frozen data.
Sarah: Bench test — like running a controller simulation on recorded plant data instead of closing the loop on the real process. You see how the algorithm would have acted, but you don't see the patient's response, the follow-up decisions, the downstream cascade.
Laura: Right. No causal claim about ordering behavior in practice. The post says "under a single standard prompt, every AI system suggested more tests." But we don't know the prompt engineering, the context window, whether the model saw the physician's note before generating its plan — that's leakage risk.
Sarah: Leakage — when test data contaminates the model's input, like training on the validation set. If the LLM sees the doctor's actual orders in the note, it's not independent reasoning; it's pattern matching.
Laura: And the independent check is blunt: the claims appear nowhere outside Reddit. The NEJM AI link is paywalled or broken. So we have a conference abstract level of evidence at best.
Sarah: Which hasn't stopped the thread from treating it as settled science. The post text reads: "Under a single standard prompt, every AI system we evaluated suggested more diagnostic tests..." — presented as fact.
Laura: The strongest view in the comments is that this proves LLMs are unsafe for clinical deployment because they'll bankrupt the system. The counter-view: maybe physicians under-order due to time pressure, and the LLM is catching things humans miss. But nobody has outcome data.

FDA's Clinical Decision Support guidance — that's the framework that decides whether software is a regulated device or just decision support — hinges on whether the clinician can independently review the basis for the recommendation.
Laura: If the LLM says "order these tests" and the physician clicks "accept" without independent judgment, that's a device function. If the LLM says "here's my reasoning, here's the evidence, you decide," it might stay in the non-device CDS category. But this study's prompt design — single standard prompt, no clinician-in-the-loop evaluation — doesn't map to either cleanly.
Sarah: It's like validating a safety interlock by checking if it trips in simulation, but not testing whether the operator can override it when it false-trips. The human-machine interface is the critical safety layer.
Laura: And the Microsoft sequential diagnosis benchmark we covered Friday — that evaluated iterative history-taking and test-ordering efficiency against physicians. This study looks like a static snapshot: one prompt, one output, compare costs. No sequential reasoning, no hypothesis revision.
Sarah: Static versus dynamic. Open-loop versus closed-loop. The benchmark measured how many questions the model needed to reach a diagnosis — that's a process efficiency metric. This study measures cost of the output plan — that's a resource consumption metric. Different validation targets.
Laura: The verdict: the claim that LLM-recommended care costs more in this retrospective setup is plausible but unconfirmed — primary source unreadable, no independent replication. The causal claim about ordering behavior in practice is not supported by the design. The "hallucination-adjacent" framing is a useful hypothesis: over-cautious generation as a failure mode worth quantifying in prospective trials.
Sarah: And the FDA CDS lens matters because if these models get deployed as "decision support" without device oversight, the validation bar stays at "does it run?" not "does it improve outcomes at acceptable cost?"
