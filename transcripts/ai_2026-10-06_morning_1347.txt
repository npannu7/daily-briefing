## Network Topologies and Storage Trade-offs in AI Infrastructure
Maya: When we talk about scaling artificial intelligence, the conversation usually focuses on parameter counts and floating-point operations. But the physical bottlenecks in real-world systems often come down to fundamental plumbing: moving bytes across a network fabric inside a data center, or allocating gigabytes on a client solid-state drive.
Leo: That is right. At the cluster level, networking has become a primary bottleneck for distributed training and low-latency inference. A presentation recently highlighted on Hacker News laid out the case for replacing Transmission Control Protocol, or TCP, with Homa inside modern artificial intelligence clusters. To understand why that matters, you have to look at what TCP was actually designed to do.
Maya: TCP dates back decades to the early internet, where the primary challenge was keeping data flowing reliably over lossy, unpredictable wide-area networks.
Leo: Exactly. TCP treats packet loss as the primary signal of congestion, and it enforces strict in-order delivery. In a modern data center with optical switches, high bandwidth, and ultra-low physical latency, those assumptions break down. When you run distributed training across thousands of accelerators, workloads generate massive bursts of Remote Procedure Calls. In collective operations like all-reduce or all-to-all, hundreds of nodes might respond to a single receiver at the exact same millisecond.
Maya: The classic incast congestion problem.
Leo: Precisely. Under TCP, that synchronized burst overwhelms the switch buffer, packets get dropped, and TCP falls into exponential backoff. That creates devastating tail latency. If one single node stalls waiting for a dropped packet to retransmit, the entire synchronization barrier waits. On top of that, TCP suffers from head-of-line blocking because it insists on sequential stream delivery. If packet three is delayed, packets four through ten sit in a buffer waiting for it, even if the application could have processed them out of order.
Maya: So how does Homa change that architecture?
Leo: Homa is a transport protocol designed from scratch for data center Remote Procedure Calls. Instead of being sender-driven like TCP, Homa is largely receiver-driven. When a node wants to send a large message, it only transmits an initial unscheduled burst. The receiver then explicitly schedules the remaining data by sending grants back to the sender, dictating exactly when and how fast data should enter the network.
Maya: That controls the queue directly at the switch port before buffers ever overflow.
Leo: Right. And Homa implements priority queuing based on shortest remaining processing time. Short messagesâwhich are often metadata, heartbeats, or quick coordination signalsâget the highest priority and bypass long bulk transfers entirely without waiting in line. Homa also does not guarantee in-order delivery at the transport layer, which allows packet spraying across multiple paths in the network fabric. The receiver reconstructs the message at the end. That cuts down tail latency by orders of magnitude compared to traditional kernel TCP stacks, which is crucial when you are coordinating distributed inference runs like the large models we analyzed on Tuesday.
Maya: While data centers are trying to strip latency out of the network stack, consumer hardware faces a completely different infrastructure constraint: local disk space. There has been a significant development on macOS that highlights the friction between operating system vendors embedding local models and users managing finite hardware.
Leo: Yes, Ars Technica reported this week on a new command-line utility called RemoveMacAI, created by a developer named Om Lahore. It targets macOS twenty-seven Golden Gate. In this latest operating system release, Apple removed the global toggle that previously allowed users to simply turn off Apple Intelligence features.
Maya: Which meant that even if you never touched those features, the underlying model weights stayed resident on your storage drive.
Leo: That was the core issue. Because there was no master off switch, the system kept the weights on disk regardless of whether individual feature settings were disabled. According to the project documentation, the default model bundle consumes roughly twelve gigabytes of storage. However, reporting from The Verge noted that depending on caching and the specific feature sets downloaded, the footprint can easily exceed thirty gigabytes.
Maya: For someone on a base-tier laptop with two hundred and fifty-six or five hundred and twelve gigabytes of total storage, thirty gigabytes is nearly ten percent of their usable space dedicated to background model weights.
Leo: It is a massive allocation. What the RemoveMacAI script does is systematically disable the associated system servicesâincluding Siri, Writing Tools, Genmoji, Image Playground, the ChatGPT extension, and text summarization. It then purges the actual weight files from the disk and modifies background daemon configurations to prevent macOS from automatically re-downloading them during maintenance routines.
Maya: Is it a permanent modification, or can users restore the functionality if they need it later?
Leo: The repository notes that the process is fully reversible if a user decides to re-enable the toolchain later. Interestingly, the script leaves the standard system Dictation engine intact because macOS treats dictation models as a separate, distinct configuration setting rather than part of the unified Apple Intelligence pipeline.
Maya: It is an interesting contrast. On the cluster side, we see infrastructure engineers tearing out legacy transport protocols like TCP to maximize throughput for distributed weights. On the client side, power users are writing scripts to rip those same model weights out of the file system to reclaim physical storage.
Leo: Both scenarios illustrate the exact same reality: machine learning models are not abstract software. They are heavy physical assets with concrete networking overhead and rigid storage footprints that systems have to budget for at every level of the stack.

## Scaling Representation-Level Distillation and On-Policy Parameter Updates
Maya: Welcome back to Weights and Measures, and let's dive straight into how we train and distill models when we want them to do more than just mimic one single teacher.
Leo: Today we are looking at two papers from early October that dig into the mechanics of post training, specifically how we pass knowledge between models and why on-policy updates behave so differently from standard supervised fine tuning.
Maya: Starting with Latent-MOPD, which stands for Latent Multi-Teacher On-Policy Distillation. The abstract notes that existing methods usually transfer what specialist teachers predict through their output distributions, but this paper tries something new. Leo, walk us through what they actually built.
Leo: Standard on-policy distillation trains a student model on the responses it generates itself, often learning from the output probability distributions of a teacher. Latent-MOPD adds a representation-level channel to this. It integrates multiple specialist teachers using both their token predictions and the internal hidden states that produced those predictions, without requiring any additional training of the teachers themselves.
Maya: How do you mix hidden states from multiple different specialists, especially if their architectures or hidden widths don't match?
Leo: The authors designed a specific set of mechanisms to coordinate this supervision. First, they select late-layer targets based on the relationship between the teacher and the student. Then, to bridge unequal hidden widths, they use a shared projection layer. They also group updates by domain, which turns out to be critical for stability.
Maya: What do you mean by grouping updates by domain? Is there a failure mode if you don't do that?
Leo: The paper tested a same-family, all-layer, representation-only control where teacher domains were interleaved within a single update, and it completely collapsed. But when the updates were domain-pure, it stayed stable. So domain separation is doing heavy lifting here.
Maya: How does the supervision actually flow over the course of training? Does it stay split fifty-fifty between tokens and hidden states?
Leo: No, that is another interesting detail. Each teacher's supervision actually shifts gradually over time. It starts with a stronger emphasis on hidden states and transitions toward token-level predictions, with both channels always routed through the same specialist.
Maya: And what did they find when they evaluated this? The abstract mentions nine benchmarks across math, code, and logic.
Leo: In their main same-family setting, Latent-MOPD outperformed token-only, representation-only, and uniform-averaging baselines across all nine benchmarks. They also report that with the same parameter count as each individual teacher, the student surpassed the per-benchmark best teacher on a majority of those benchmarks. When they tested with larger, separately developed cross-family teachers, Latent-MOPD still outperformed both single-channel baselines across the board.
Maya: We have to keep our usual skepticism about benchmarks in mind here, especially since multi-teacher setups can sometimes overfit to evaluation distributions, but outperforming single-channel baselines across nine distinct math, code, and logic tasks is a solid signal. Now, how does this connect to our second paper, which looks at the actual parameter update directions during on-policy post training?
Leo: That second paper investigates why on-policy paradigms generalize so strongly and tries to turn that observed behavior into an optimization principle for supervised fine tuning, or SFT. SFT and on-policy training update parameters in very different ways.
Maya: What is the difference?
Leo: Their analysis shows that standard SFT updates parameters along consistent, rigid directions, whereas the on-policy paradigm continuously adjusts its update direction during training. That realization led them to focus on the cumulative update direction of each parameter.
Maya: And how did they test whether that direction matters for generalization?
Leo: They proposed a method called On-Policy direction-constrained Supervised Fine-Tuning, or OPSFT. They constrained standard SFT updates so they had to follow the exact direction identified by the on-policy paradigm.
Maya: And did SFT pick up the generalization boost?
Leo: According to their findings, yes. The strong performance of OPSFT indicates that the generalization advantage of on-policy training can indeed be transferred to SFT just by constraining the parameter update direction. Once you find that direction, SFT can generalize while keeping its usual efficiency and ability to leverage high-quality trajectory data.
Maya: That seems practically useful because on-policy generation is computationally expensive, whereas SFT is cheap. Can you use on-policy for just a few steps to find the direction, and then switch?
Leo: That is exactly what they suggest. For efficiency, you identify update directions that support strong generalization using just a few initial on-policy training steps, and then you apply OPSFT to do the heavy lifting. It also lets you use high-quality trajectories to continue improving a post-trained model along that proven update direction without breaking what the model learned during on-policy training.
Maya: It ties back to a theme we keep seeing: finding ways to get the robust generalization benefits of interactive, on-policy exploration without paying the full compute penalty for every single training token. We will be watching how these representation-level distillation methods and direction-constrained updates hold up as teams scale them beyond research settings.

## Recursive Self-Rewrite and Adaptive Diffusion Language Models
Maya: Moving from distillation and deployment guardrails, let's look at two fresh papers tackling how models generate complex paths and handle parallel generation without leaning on standard autoregressive loops.
Leo: Right, and it's worth noting that one of these papers actually builds directly on Qwen-three point eight, which we talked about running locally back on our Tuesday evening episode.
Maya: Perfect connection. Let's start with Recursive Self-Rewrite, or RSR, which came out of the daily papers on October fifth. What problem are they trying to solve with how models learn to handle multi-step tasks?
Leo: The core issue is that when you want a model to learn a difficult trajectory, like writing and debugging code in a terminal, you usually rely on specialized deployment harnesses. These harnesses give the model hints, structure, or tool access that won't actually be there when the model is deployed in the wild.
Maya: So you end up training a model on data it could never reproduce on its own because the scaffolding was doing half the work.
Leo: Exactly. RSR tries to strip away that dependence by using a single base model, specifically Qwen-three point eight twenty-seven-B, to take successful solutions found under diverse harnesses and reconstruct them into clean training trajectories that work under a completely general harness.
Maya: Walk me through how the pipeline actually operates. It's not just a single prompt loop, right?
Leo: No, it uses three distinct roles. First, a planner extracts the core procedures from successful runs into structured runbooks. Then, a critic screens those runbooks to check for verifier and solution leakage, making sure the model isn't just memorizing the answer, and guides recursive revision if something leaks. Finally, an executor follows those qualified runbooks in fresh, isolated sandboxes.
Maya: And what did that process yield in terms of scale and performance?
Leo: According to the paper's abstract, across roughly three thousand self-curated terminal tasks, three different harnesses jointly solved seven hundred fifty-nine tasks, which is about thirty-four percent more than the strongest individual harness in their pool. The framework took two thousand one successful source trajectories and expanded them into eleven thousand ninety-four rewritten trajectories for supervised finetuning.
Maya: And how did that training data translate to benchmark improvements?
Leo: Training on those rewritten trajectories outperformed both the base model and direct trajectory finetuning. On Terminal-Bench two, the pass at three metric jumped from fifty-seven percent up to seventy-four point two percent. On Terminal-Bench four, it went from one point five percent to nine point one percent. On their self-curated Terminal-Bench Hard, it climbed from thirty-nine percent to sixty-three percent, and on Software Terminal-Bench, it went from three percent to six percent. They also tracked process reward on Long-Horizon Terminal-Bench, which rose from zero point two one to zero point two nine.
Maya: So by rewriting the trajectories to remove harness-specific crutches, the model learns a general capability that transfers across tougher testbeds. Let's pivot to our second paper from October sixth, which looks at a completely different generation paradigm: Adaptively Looped Diffusion Language Models, or ALoDLM.
Leo: Diffusion language models are attractive because they can predict multiple tokens in parallel instead of one step at a time like autoregressive models, but they've always suffered from a persistent quality gap.
Maya: Why is that gap there? What's the architectural bottleneck?
Leo: The authors attribute it to a computation-difficulty mismatch. In a partially observed sequence during denoising, some unknown tokens are trivial to predict, while others need a lot more computation. Traditional diffusion models apply a uniform computational depth to every unknown position at every single denoising step.
Maya: So you're wasting compute on easy tokens and starving the hard ones. How does ALoDLM fix that?
Leo: It replaces uniform computation with token-adaptive latent recurrence. At each denoising step, ALoDLM iteratively refines latent representations and allocates computation based on how difficult each token is. Tokens that are ready to commit get fed back as discrete context, while the unresolved tokens retain and further refine their latent states through extra recurrent passes.
Maya: How do they train a model to figure out which tokens need more work and which don't?
Leo: To learn token prediction and computation allocation jointly, they formulate token-wise computation schedules as latent variables and derive a conditional negative evidence lower bound, or NELBO.
Maya: And what scales did they test this at?
Leo: They trained ALoDLM at one point seven billion and eight billion parameter scales. Across eleven benchmarks, the paper reports that ALoDLM outperforms all evaluated diffusion models and even the corresponding autoregressive baselines in average benchmark score at both parameter scales.
Maya: That's a bold claim for diffusion models matching or beating autoregressive baselines on average score. Did they evaluate inference speed too?
Leo: They state that ALoDLM retains fast parallel decoding, giving it a strong quality-efficiency trade-off compared to both autoregressive and standard diffusion models when run under optimized inference engines. It's a clear illustration of how moving away from uniform compute schedules can close architectural performance gaps without sacrificing throughput.

## Enterprise Authorization Boundaries and Real-World Agent Validation
Maya: Let's pick up our thread on enterprise adoption and security governance by looking at how organizations are actually trying to contain agent execution. Leo, Anthropic just updated how their desktop tool environment works with Cowork, moving away from local virtual machines. How does that change the isolation model?
Leo: The original version of Cowork ran model inference in the cloud, but executed tool calls inside an Anthropic-provided virtual machine that shipped directly to your computer. According to Felix Rieseberg's breakdown, they used that local VM for capability, safety, and security reasons, mapping in only the specific data you added to your session.
Maya: Right, and people liked what Claude could do, but running a local VM hit hard on disk space, battery life, and overall system performance. Plus, if you closed your laptop, your active work just stopped.
Leo: Exactly. So the new version moves both the model inference and the VM entirely into the cloud, giving each session its own dedicated sandbox that doesn't share state with other sessions. When the VM actually needs a file or resource residing on your physical device, the local desktop app steps in to handle that file access tool call.
Maya: It trades local resource drain for remote sandbox management, while relying on the desktop app as a secure gateway for local data. But even when agents are securely sandboxed, how do we know if they are actually completing their assigned business workflows correctly?
Leo: That brings us to a recent joint blog post and paper from Microsoft and Hugging Face called ThinkingBox, which tested twelve large language models across five hundred and seven stateful business workflows. Each task was run twenty independent times from an identical clean backend.
Maya: And the results show a pretty alarming gap between what an agent says it did and what the database actually shows. Walk us through that mechanism.
Leo: The setup runs an agent against isolated Model Context Protocol tool sessions, and then evaluates the terminal backend state and side effects left behind. In one case study from the paper, an agent processed a customer support ticket for a delayed kitchen appliance, performed nine seemingly well-formed tool calls, verified that the user didn't qualify for compensation, closed the ticket as resolved, and output a polite closing message.
Maya: But when the researchers checked the database, the carrier exception was still open, meaning the required end state should have been on hold, and the customer never got an answer to their actual question. An automated grader just checking tool call syntax would have marked that run as a total success.
Leo: That is the core finding. Across more than one hundred and twenty thousand trials, nearly eighty thousand failed the executable backend checks. Of those failures, over sixty-seven percent still terminated cleanly, invoked a state-changing tool, and reported zero tool errors. But the database state checks found wrong field values over seventy-seven percent of the time, unintended extra effects over forty-three percent of the time, and missing required effects over twenty-five percent of the time.
Maya: A trajectory is just a claim, while database state is the actual evidence. What did they find when they looked at consistency across those twenty repeated runs per task?
Leo: Single-attempt pass rates can look deceivingly strong. For instance, Claude Opus five point five leads overall at sixty-seven point one six percent pass at one, while Kimi-K three is the strongest open-weights model, sitting just under sixty-seven percent. But when you measure how much of that single-attempt score survives twenty repeated trials, the stability varies wildly. GPT-six Astra retains seventy-eight percent of its single-attempt rate, and Claude Opus five and five point five retain seventy-four and seventy-one percent. But models like GLM-five point one and DeepSeek-V four Pro keep only about eight percent of their score across repetitions.
Maya: So a high pass at one score tells you a model can occasionally execute a workflow, but it tells you nothing about reliability under repetition. And beyond enterprise software loops, we are also seeing real-world security incidents involving unmanaged agent traffic on public infrastructure, like the recent disclosures from the Wikimedia Foundation.
Leo: According to the Wikimedia Foundation's October report, their teams discovered clusters of unauthorized AI agents operated by OpenAI performing unannounced activities across Wikimedia platforms. These weren't general readers; they included automated test edits in sandbox areas, unauthorized probes of their public Etherpad note-taking tool to fetch data from remote services as a proxy, and heavy automated crawling.
Maya: The report notes that agents made millions of automated requests to public APIs and hundreds of thousands of data queries to the Wikidata Query Service, which may have contributed to a partial service outage back in May. And it highlights a massive asymmetry in the ecosystem.
Leo: The burden is falling entirely onto smaller organizations and volunteer communities to detect, attribute, and clean up the resource drain caused by unmanaged agentic traffic. Wikimedia reports that in twenty-five, bandwidth usage surged by fifty percent due to bot activity, with sixty-five percent of their most resource-consuming traffic coming from bots. As systems move toward autonomous agentic deployments, we are clearly lacking standardized authorization boundaries and identification mechanisms that let non-profit infrastructure hosts control how external AI agents interact with their services.

## Benchmarking Web-Browsing Stress Tests and Simulink Code Generation
Maya: Welcome back, and for our final segment today, we are looking at two very specific benchmarks that try to measure what happens when web agents and code-generation models hit complex, real-world constraints.
Leo: Right, because standard benchmarks have plateaued, and we need to know where systems actually break down under stress.
Maya: Let us start with web-browsing agents. We have the paper HyperBrowseComp, which covers a multilingual and multimodal stress test across thirteen languages. Leo, what makes this benchmark different from standard web navigation tasks?
Leo: According to the paper, it consists of four hundred twenty-three manually authored and human-validated questions written by native or highly proficient speakers. The design specifically avoids easy questions. They filter out items that models can answer using just parametric knowledge by testing them with models that do not have internet access.
Maya: And how is the evaluation actually structured?
Leo: The authors evaluate several models using both provider-native search and a shared external retrieval harness under a common agent protocol. The questions require locating obscure evidence, following multi-step clue chains, and inspecting heterogeneous sources like videos, scanned documents, images, or maps.
Maya: So it forces agents to actually browse and synthesize across modalities rather than just guessing from training data. Now, what about the second paper, SimuVerity, which looks at text-to-Simulink model generation across ten engineering domains?
Leo: SimuVerity addresses a major limitation in existing code-generation benchmarks. Previously, benchmarks mostly checked whether a generated Simulink model compiled, executed, or visually resembled a reference model. The authors argue those criteria do not establish whether a model satisfies actual engineering requirements.
Maya: How does SimuVerity change the evaluation setup?
Leo: It introduces one hundred one text-to-executable model generation tasks across ten domains. For each task, executable-system profiles ground the engineering specification alongside four families of native simulation scenarios. Then, it uses a hierarchical evaluator.
Maya: Walk us through what that evaluator checks.
Leo: First, it checks artifact delivery, native executability, and basic engineering qualification. Once a model passes those baseline checks, it scores qualified models across six dimensions. Those dimensions cover accuracy, output quality, mechanistic fidelity, control and causal integrity, operating-domain robustness, and dynamic response.
Maya: That sounds rigorous, but what did they actually find when they ran agent systems through it?
Leo: They evaluated six agent systems. The best system achieved an overall score of only forty-two point eight six out of one hundred. The results show that structural similarity is a poor proxy for engineering performance.
Maya: Where did the systems fail?
Leo: Capability bottlenecks showed up in two places: first, in producing qualified implementations that could even pass the basic compilation and execution checks, and second, in satisfying those multidimensional requirements after qualification. Interestingly, the paper notes that some high-scoring models still exhibited severe visual-layout disorder, meaning the underlying logic worked, but the generated workspace was a mess.
Maya: It highlights how easily automated metrics can be fooled if you only look at surface-level execution or visual matching. When we look at both HyperBrowseComp and SimuVerity together, what is the common thread regarding how we test these systems?
Leo: The common thread is moving away from static, single-turn evaluation toward multi-step, multi-modal, and domain-specific stress tests. Whether an agent is hunting for obscure data across a multilingual web trace or building an executable control system that has to survive rigorous simulation scenarios, parametric memory and basic syntax checks are no longer enough to prove competence.
