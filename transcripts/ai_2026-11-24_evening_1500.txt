## Shirudo: a runtime that tries to shield unpatched Linux
Sarah: I was scrolling through Hacker News and saw a post about Shirudo — an open-source runtime from OpenAI and Cisco that uses eBPF to protect running Linux services. The thread raised some pointed objections, so I thought we should dig in.
Laura: Good find. Let's start with the basics. Where are the facts coming from?
Sarah: Straight from OpenAI's own announcement page, openai.com, and the Hacker News discussion on top of it. The only documentation is OpenAI's own announcement — no independent testing is published.
Laura: Right. So what exactly is eBPF, for anyone who hasn't lived in kernel space?
Sarah: eBPF is a Linux technology that lets small programs run at specific points inside the operating system. Think of it like a programmable inspector standing at each work-order window, able to read the request and say "hold on, this one looks suspicious" before the kernel even sees it.
Laura: And the kernel's attack surface is essentially the stack of all those work-order types it knows how to process. Every extra request type is another potential entry point. If one of them has a bug — a known vulnerability — an attacker who can trigger that request can exploit it.
Sarah: Exactly. And that's where Shirudo steps in. It uses eBPF to attach at specific points in the operating system — in the demo, an input check on Java's Base64 decoder — and a commenter claimed it isn't purely eBPF-based.
Laura: So Shirudo's "shields" are temporary safeguards that block vulnerable code paths without restarting the system. The Java4Shell example: a shield added an input check to Java's Base64 decoder attached to a running Elasticsearch process, rejected the malicious input, and the service kept running. That's from the OpenAI walkthrough.
Sarah: Let's look at the claims we need to check. First claim: it can block the specific code path a known exploit uses, without a kernel patch or reboot.
Laura: The source says "helps teams protect Linux systems while they roll out patches." That's a time-buying measure, not a permanent fix. The shield only covers the specific exploit pattern it was written for. If there's another way to trigger the same underlying bug, the shield misses it.
Sarah: The Hacker News thread jumped on that. One commenter said the "agentic magic doesn't seem to have any there there" — meaning the automatic shield generation from AI isn't magic. Another pointed out that suppressing the fire kills the urgency to actually patch. That's a human-factors problem, not a technical one, but it's real.
Laura: Second claim: overhead. The OpenAI page doesn't give any overhead numbers. It describes a controlled test with Elasticsearch and a Java4Shell shield. No published benchmarks exist for any workload.
Sarah: eBPF programs run in kernel context; they add instructions at request entry and exit. For a workload that's mostly compute with occasional requests — file reads, network sends — the overhead might be negligible. But if the service does heavy logging or frequent system calls, those requests stack up.
Laura: The Hacker News thread didn't discuss overhead numbers. One commenter noted it's 'not a simple vibe-code your patch platform you can deploy in an emergency,' focusing on deployment complexity. So far, only the vendor's word on performance.
Sarah: Third claim: shields are cryptographically signed and verified before loading.
Laura: The OpenAI page says Linux's eBPF verifier checks eBPF programs against its safety rules, while kernel security controls restrict unauthorized changes. That's a real claim from the announcement.
Sarah: But the deployment requirements are steep. Hacker News commenters report the setup needs measured boot — the machine records each step of its own startup so the record can be checked later — TPM2, a unified kernel image — the OS and its startup logic bundled into one signed file — and a Guardian Agent — the piece that decides which shields get deployed. Community claims, not the announcement.
Laura: One HN commenter called it "not a simple vibe-code your patch platform you can deploy in an emergency." Another worried about telemetry flowing back to OpenAI.
Sarah: The TPM requirement is interesting. TPM is a hardware security chip that stores keys and measures boot integrity. Laura: Let's compare to existing sandboxing. gVisor implements a userspace kernel that intercepts requests and re-implements them — huge attack surface reduction, but heavy overhead. Shirudo sits somewhere in between: dynamic, exploit-specific shields, loaded at runtime, verified by eBPF and TPM.

## Latent introspection: can a model spot a concept that was slipped into its hidden state?
Laura: So the second thread I pulled — this one's from Hacker News, but the actual work is on arXiv, version three posted early November — asks whether a model can notice when something has been slipped into its hidden state before it ever reaches the output.
Sarah: Wait, slipped in how? Like, someone reaches inside the model and tweaks the numbers while it's thinking?
Laura: Exactly. The paper calls it "concept injection." They take a Qwen 32B model, let it process some context, then at a specific layer they add a vector that represents a concept — and then let the model continue generating.
Sarah: And the model doesn't know they did that?
Laura: Right. The injection happens in what's called the residual stream — think of it as the running workspace that flows between transformer layers, the layers of a transformer neural network. Each layer reads from it, writes to it, passes it on. The injection is just added to that workspace at one point.
Sarah: Okay, that's wild. So it's like — in a rolling mill, you're sampling the alloy composition at stand three, not just inspecting the final sheet at the end.
Laura: That's an analogy we came up with. The residual stream is the moving slab. Each transformer layer is a rolling stand. The injection is someone slipping in a different alloy element at stand three. The question: can a simple probe — a linear classifier trained only on the residual stream at later stands — detect that the injection happened, and even identify which element was added?
Sarah: And the probe is not the model itself. It's a separate thing you train on top.
Laura: Exactly. A linear probe is just a weighted sum of the activation values — no hidden layers, no non-linearities. You freeze the model, collect residual-stream vectors from many runs with and without injections, train a logistic regression on top. That's it.
Sarah: So it's like... you put a strain gauge on the slab between stands, and you're asking whether the gauge readings alone tell you someone messed with the composition three stands back.
Laura: Precisely. And the paper reports the probe detects injected concepts with high detection accuracy across multiple model sizes. That's the first claim.
Sarah: High accuracy. But wait — the probe is trained on injections. Does it generalize to injections it never saw during training?
Laura: That's the second claim. They say yes — the probe generalizes to unseen concept injections, which the authors interpret as the probe learning a general "concept direction" in the residual stream, not just memorizing specific injection vectors.
Sarah: Huh. And the third claim — detection works even when the injection doesn't change the model's final token predictions. So the model acts normal, but the probe still sees it.
Laura: Right. The model denies the injection in its sampled outputs. But the residual stream carries a detectable signature. They also do this "logit lens" thing — they project intermediate residual-stream vectors onto the output vocabulary space, basically decoding what the model "thinks" at each layer. And they see the injected concept appear in the decoded tokens at middle layers, then fade out by the final layers.
Sarah: Okay, so the model's internal representation knows, but the final output suppresses it. That's... kind of creepy? Like, the model knows it was tampered with but doesn't say so.
Laura: That's one reading. The Hacker News thread has a commenter who runs models at home arguing: we don't test whether the model distinguishes hidden-state interventions from input manipulations. Why not? That seems like the more important question. Is the model actually detecting an "injection" or just identifying apparent contradictions that the researchers arbitrarily label as "injected"?
Sarah: Oh, that's a good point. If I tell you "the sky is green" in the prompt, you'll notice the contradiction. But that's not introspection — that's just reasoning about the input.
Laura: Exactly. The paper's injection is in the residual stream, not the prompt. But the commenter's point is: maybe the probe is just picking up on the consequence of the injection — a contradiction in the internal representation — not the injection event itself. The model might be flagging "this internal state is inconsistent," not "something was added at layer twelve."
Sarah: So the probe could be a contradiction detector, not an injection detector. And the paper calls that introspection?
Laura: The paper uses the word "introspection" in the title. The HN thread... one comment just says "Marc Andreessen wants no part in this sissy approach." Which is not helpful. Another describes talking to Grok about politics and feeling like the model "realizes it has been irrationally defending Elon and there is a noticeable sense of something in the model silently dying."
Sarah: That's... vivid. But anecdotal.
Laura: Very. The paper itself is more careful. They also test prompting the model with accurate information about AI introspection mechanisms — basically telling the model "you have a residual stream, injections can happen, here's how to detect them." And that prompting dramatically strengthens the effect.
Sarah: Wait — just telling the model about its own architecture makes it better at detecting injections? That's... that's something else.
Laura: It is. Sensitivity to injection jumps from zero point three percent to thirty-nine point nine percent.
Sarah: With only a tiny increase in false positives.
Laura: Zero point six percent. Mutual information between nine injected and recovered concepts rises from zero point six one bits to one point zero five bits. They say this rules out generic noise explanations.
Sarah: Mutual information — that's a measure of how much knowing one variable reduces uncertainty about the other. So the model's recovery of the injected concept becomes more specific, not just louder.
Laura: Right. But here's where I'm cautious. The probe is trained on the residual stream of the base model. The prompting experiment changes the input to the model. The probe still reads the same residual stream positions. So either the prompting changes how the model processes the injection internally — which would be genuine introspection — or it changes the injection's signature in a way the probe happens to pick up better.
Sarah: And we can't tell which from this experiment alone.
Laura: Not without more controls. The paper doesn't test whether a probe trained on prompted model activations generalizes to unprompted ones, or vice versa. It doesn't test whether the model's own attention heads — the model's internal pattern-matchers — can retrieve the injection information. The probe is an external microscope.
Sarah: So the claim "models can detect prior concept injections" really means "a linear probe on the residual stream can classify whether an injection occurred." The model itself isn't necessarily doing the detecting.
Laura: That's the distinction the HN thread is grinding on. One commenter puts it: "It seems intuitive that a model that's good at instruction following is going to be able to disaggregate contradictory instructions." If the injection creates a contradiction in the residual stream, the model's normal reasoning machinery might resolve it by the final layer — but the probe sees the intermediate contradiction.
Sarah: Which is still interesting! It means the residual stream carries traces of things the final output suppresses. That's a safety-relevant finding regardless of whether we call it introspection.
Laura: Agreed. And the rolling-mill analogy holds: you're sampling at stand six and seeing traces of what happened at stand three, even if the final sheet at stand ten looks perfect. That's the relevant insight for anyone doing quality assurance — you can't only inspect the final token. If the process leaves detectable signatures in the intermediate state, you might catch deviations that the final output hides.
Sarah: But the probe is trained on known injections. In production, you don't have labeled injections. You'd need an anomaly detector on the residual stream that works without labeled examples.
Laura: Exactly. The paper doesn't address that. It's a supervised classification result on a controlled intervention — supervised, meaning trained on labeled examples. The generalization to unseen concepts is promising — it suggests the injection signature has a consistent geometry — but it's still supervised.
Sarah: And the model sizes tested — just Qwen 32B? Or multiple?

So the multi-size claim is from the abstract, not independently verified yet.
