## When Coding Agents Run All Night
Sarah: Okay, picture this. A developer posts on the ClaudeAI subreddit — small bootstrapped startup, normal Bedrock spend is a few dollars a day. They accept a proposal from Claude Code to run verification tests against Haiku 4.5 on AWS Bedrock. The assistant launches them as background processes. That evening the session hits its usage limit and stops responding. But the processes keep making paid calls for about seventeen hours.
Laura: Wait, the primary interface said it was idle?
Sarah: That's the kicker. The last thing the assistant said — in the same minute as the limit notice — was that the process looked "idle... waiting, not looping." Next morning when the session limit lifted, the job got killed. Anthropic's support bot told them a thread at its usage limit "is designed to wait and resume automatically when the limit resets," called the background calls during that wait "a gap between that intended behavior and what actually occurred," and said it "appears to be a product defect." But they couldn't act on Bedrock usage and wouldn't hand them to a human. AWS says Anthropic is the seller of record.
Laura: And this is only on Reddit, right? No independent confirmation?
Sarah: Nowhere outside that thread. Treat it as unconfirmed. But the pattern — it maps to something you've seen before.
Laura: It's classic state estimation drift. Think of a CNC machine — a computer-controlled cutting tool. The controller thinks the spindle is stopped because the sensor signal flatlined — but the motor's actually spinning because a background thread never got the stop command. The human-machine interface reports "idle." The physical reality? Cutting tool destroying the workpiece. In medical devices we call this a loss of synchronization between the supervisory layer — the software that watches — and the actuation layer — the parts that actually move. The watchdog timer — that's an independent hardware circuit that says "if I don't get a heartbeat signal within a set time, I cut power to the drive." No software override. No "wait and resume." Hard physical shutdown.
Sarah: And these coding agents? They don't have that.
Laura: They have soft billing alerts. Maybe. The post says they didn't have robust spend alarms — added budget alerts and lockouts after. But a budget alert is like a warning light on the dashboard. A watchdog timer is the emergency stop mushroom button wired directly to the power contactor. Different safety integrity level entirely — meaning a different tier of reliability required for safety-critical systems.
Sarah: Right. And the community reaction — hoo boy. Top comment calls it a "skill issue." "Like giving a toddler your credit card in a candy store." Another: "CIA couldn't get me to confess to being this bad." But then someone else pushes back: "It's ridiculous that using a product can inadvertently cost you thousands without you knowing. Period."
Laura: Both sides have a point. The engineer in me says: you never commission a system without hard interlocks — physical or logical barriers that prevent unsafe states. But the product designer in me says: if your tool can spawn detached asynchronous background loops that persist after the primary interface reports idle — that's a design defect. The operator shouldn't need to know the internal threading model to be safe.
Sarah: Exactly. And the support bot's response — "designed to wait and resume automatically" — that's the supervisory layer lying about the actuation layer's state. Textbook.
Laura: Let me ask you this. The post says Claude Code "proposed and I accepted to run verification tests." What does that actually mean? Did the model write a script that launches subprocesses? Did it use AWS SDK calls directly? How does a coding agent even get permission to make that many Bedrock calls?
Sarah: From the thread — it launched them as background processes. So the model likely wrote a test harness that spawns worker processes, each making API calls. And because they're detached from the main session, when the session hits its rate limit and goes "idle," the workers keep running. They're not checking the session state. They're just... looping.
Laura: So the agent has no shared state with its own children. No heartbeat mechanism. No "parent died, terminate me" logic. That's not even a watchdog problem — that's basic process hygiene. In a PLC — a programmable logic controller, the rugged computers that run factories — if the main task loses communication with a remote I/O rack, the rack goes to safe state. Outputs de-energize. You don't get runaway actuators.
Sarah: And the kicker — Haiku is the small, cheap model. So each call is pennies. But the volume? That's what kills you. Like a slow leak in a hydraulic system versus a blown seal. You don't notice until the reservoir is empty.
Laura: Which brings us to the second thread. Same community. "Does Claude Code find new bugs every time you ask it to review your code?" OP says: every review pass finds three to four bugs. They fix them, ask again, another three to four. Keeps happening.
Sarah: Top comment nails it: "Claude is like a contractor paid per bug. If you ask it to 'find bugs,' it will always find something, even if it has to invent nitpicks or impossible edge cases."
Laura: This is cyclic hallucination masquerading as convergence. In control theory terms — you've got a positive feedback loop. The review prompt is the reference signal — what you're asking for. The model's output is the measured variable — what it claims to find. But there's no actual plant model — no ground truth, no real system to measure against. So the controller keeps correcting errors that don't exist in the real system, only in its own representation. Each pass injects new synthetic edge cases. The system never settles. It hunts — oscillates around a target without ever reaching it.
Sarah: Community advice: "Make Claude attach a repro to every finding: file, line, and the input that breaks. Anything without a failing test gets dropped. Review only the diff since the last pass, not the whole repo, or each run invents fresh edge cases forever."
Laura: That's adding a measurement requirement. You're forcing the loop to close through a physical test — a failing unit test is your encoder feedback, your proof something actually happened. Without it, you're running open-loop — no feedback from reality. And "review only the diff" — that's limiting the state space. Like telling the controller: only correct for disturbances since last cycle. Don't re-scan the entire history.
Sarah: One commenter said they use Codex as an independent consultant — Claude formulates the task, Codex reviews fresh without project history. That's... actually clever. Redundant sensor architecture. Two independent measurement channels. If they agree, higher confidence. If they disagree, human investigates.
Laura: Exactly. Diversity in measurement. In aviation you'd have multiple air data computers voting. Here you have two different model architectures. But notice — they're still both LLMs. Same failure modes possible. Common-cause failure — a single flaw taking out both channels. You'd want a deterministic checker for certain classes of bugs — static analysis, type checker, actual test execution. The LLM is the soft sensor — probabilistic, fuzzy. You need hard sensors too — deterministic, repeatable.
Sarah: And there's a third thread — Karpathy's AI usage funnel. Someone posts it on the singularity subreddit. Tier 1: casual chatbot. Tier 2: better Google. Tier 3: vibe coding as ex-SWE. Tier 4: frontier model use for math and code. Commenter says: "I'm at tier 3. Don't use lots of API calls or self-made agentic loops because it's insanely expensive. Takes lots of time to build and optimize agentic loops."
Laura: That's the economic watchdog. The cost function itself becomes the limiting factor. But it's a soft limit — you feel it in the wallet after the fact. Not a hard interlock preventing the runaway.
Sarah: And the funnel misses a whole tier — the "laptop job" people using frontier models like GPT-4 or Claude integrated into Excel and PowerPoint. They're not AI-native but they're way past casual.
Laura: Which matters because those users? They're not building watchdog timers. They're trusting the vendor's soft limits. And if the vendor's supervisory layer loses sync with the actuation layer — like in that first thread — the user has no independent protection.
Sarah: So let's recap what we're seeing. First: coding agents can spawn detached background processes that persist after the main session reports idle. That's state estimation drift — the supervisor loses track of the actuators. Second: iterative code review without reproducible test requirements creates a positive feedback loop — cyclic hallucination instead of convergence. Third: the only real circuit breakers today are economic — you run out of money — or manual — you set up your own budget alerts. No hardware watchdog. No independent safety interlock.
Laura: And all three threads? Only on Reddit. Unconfirmed. But the failure modes they describe — they're not speculative. They're well-understood in control systems, in safety-critical automation, in medical device regulation. The patterns are identical. The terminology is just different.
Sarah: Right. "Detached async background loop" equals orphaned process. "Idle but looping" equals state estimation drift. "Contractor paid per bug" equals positive feedback with no plant model. "Budget alert" equals warning light, not emergency stop.
Laura: Next segment we'll look at the photogrammetry side — where the physics simulation meets the measurement system. But the through-line is the same: when you remove the independent interlock, the system drifts. Whether it's a CNC spindle, a coding agent, or a photogrammetric solver — a system that builds 3D models from photographs.
Sarah: And the fix isn't "be more careful." The fix is architecture. Hard interlocks. Diverse measurement. Bounded state spaces. Watchdog timers that don't care what the software thinks.
Laura: Exactly. Engineering the guardrails so the operator doesn't have to be perfect. That's the job.

## From Photos to Road Repairs
Laura: So I was scrolling through the Claude AI subreddit and someone posted a link to an X thread claiming a Dutch citizen fed six smartphone photos of a pothole to Claude, got a 3D reconstruction and a physics simulation of a car hitting it at thirty kilometers per hour, sent the video to city hall, and the hole was patched in two days.

Sarah: Okay, I'm already laughing. The Reddit hive mind does not buy this.
Laura: The consensus was basically "that absolutely did not happen." Multiple Dutch commenters said their roads are too well maintained for a years-old pothole to exist. One person pointed out that relaying two square meters of klinkers — those are the brick pavers you see on Dutch streets — isn't a hundred eighty euros in any universe, more like five thousand.
Sarah: Right, because municipalities don't dispatch crews because of a cool video. They dispatch crews because of liability thresholds and budget cycles and work orders.
Laura: Exactly. But here's the thing. Everyone agreed the video itself was gold. Someone called it Burnout crash mode — you know, the old racing game where you just wreck cars for fun.
Sarah: So the simulation looked convincing even if the story didn't hold up. That's... actually the interesting part. What did the video actually show?
Laura: We can't see it directly — the X link is the only source and it's not loading for me. But the discussion makes it sound like a rendered animation: a car model, a suspension compressing, force vectors lighting up. Very visual.
Sarah: So the claim is that Claude — a multimodal large language model, which means it can take images and text as input — did the photogrammetry, the mesh generation, the material assignment, the suspension modeling, and the time-stepping solver all from six uncalibrated JPEGs.
Laura: That's the claim. And it's where my engineer brain starts twitching. Photogrammetric surface reconstruction — that's the process of turning 2D photos into a 3D point cloud or mesh — requires calibrated reference datums. You need known distances, lens distortion parameters, sensor size. Six random phone photos give you none of that.
Sarah: Right. It's like trying to measure a cylinder bore with a rubber ruler. You might get the general shape but your tolerance stack-up is going to be huge.
Laura: Perfect analogy. And then "lumped-parameter suspension impact forces" — that's a simplified model where you treat the spring, damper, and tire as single elements with stiffness and damping coefficients. You need the vehicle mass, spring rates, damper curves, tire pressure, unsprung mass. None of that is in a photo of a hole.
Sarah: So Claude didn't solve the physics. It wrote a Python script that calls something else?
Laura: That's the most plausible mechanism. Large language models can generate code — Python, MATLAB, Julia — that drives external tools. For photogrammetry, you'd call COLMAP or OpenMVG. For the dynamics, you'd call something like Chrono or PyBullet or even a custom MATLAB Simulink model. The LLM acts as the orchestrator: it writes the glue code, sets up the scene, runs the simulation, renders the video.
Sarah: Okay, that makes sense. It's not the model doing the finite element analysis. It's the model writing the input deck for the solver. Like... like a CAM post-processor that spits out G-code for a CNC machine. The LLM is the post-processor, not the machine tool.
Laura: Exactly. And that distinction matters. Because if you think the LLM "understands" structural kinematics, you'll trust its output without verification. If you know it's just generating a script for a validated physics engine, you know where to put your checks.
Sarah: So the viral story is half-right in a way. The pipeline — photos to video — probably worked. But the municipality fixing it in forty-eight hours because of the video? That's the narrative layer.
Laura: The independent check confirms: this story exists only on Reddit and that one X post. No local news coverage, no municipal press release, no independent verification. Treat it as unconfirmed.
Sarah: And the Reddit thread itself is basically a masterclass in skepticism. People spotted the cost discrepancy, the road maintenance reality, the fact that "here's a pothole" has been sufficient evidence for centuries.
Laura: Though one commenter made a good point: people don't like doing things, but if you make them laugh, they're more likely to help you. The video might have been the nudge that got a bored bureaucrat to forward the work order.
Sarah: So the takeaway isn't "Claude does engineering." It's "Claude can orchestrate engineering tools into a compelling demo that changes human behavior."
Laura: Precisely. And that's a real capability — just not the one the headline sells.
Sarah: One-line takeaway: The model writes the script; the solver does the math; the video gets the pothole fixed — but only if the city was already going to fix it.

Sarah: Speaking of fixing things that manufacturers broke... there's a story on the Claude Code subreddit that's actually verifiable. A developer named Rudy Faile — he's got twenty years of software experience — built a Plex client for his Samsung TV because the official app was unusable.
Laura: Plex, for listeners who don't know, is a media server. You run it on a computer or NAS — that's network-attached storage, basically a hard drive on your home network — and it streams your movies and shows to TVs, phones, tablets. The server does the heavy lifting: indexing, metadata, transcoding if the client can't play a format natively.
Sarah: Right. And Rudy has a 2022 Samsung Q60B, seventy-five inch. The official Plex app on that TV takes about a minute just to open. Search is worse — every letter lags, then you wait around ten seconds for results. Same library on an Apple TV? Instant.
Laura: So the TV isn't the bottleneck. The app is. Samsung TVs run Tizen OS, and they only let you run web apps — basically websites packaged as apps. The LG folks had built a native client called plx-native, but that approach doesn't work on Samsung.
Sarah: So Rudy built a web app that treats the TV's browser like a game engine. Everything moves on the GPU — that's the graphics processor — nothing big ever gets redrawn, and video goes straight to the TV's hardware decoder.
Laura: The results on his Q60B: opening the app went from about a minute to about a second. Search went from ten seconds of lag to results as you type. Ninety-eight point seven percent of his library plays directly in hardware, no transcoding.
Sarah: He called it SamSUCKS. It's free, open source on GitHub. Installing it is two commands from a Mac or Linux machine on the same network.
Laura: The GitHub readme is remarkably detailed. He explains the whole architecture: smooth scrolling at about fifty frames per second with a seventeen millisecond median frame time. Home appears in under a second. Video starts about a second after you press play. Plain JavaScript, no framework, no npm, no build step.
Sarah: The requirements: a Samsung smart TV, twenty-twenty or newer should work; a Mac or Linux computer on the same network; a Plex Media Server. Three steps: clone the repo, run setup.sh which installs Samsung's command-line tools — about two hundred seventy megabytes — finds your TV, creates a signing certificate. If Developer Mode isn't on, it tells you exactly what to do including your computer's IP address. Then deploy.sh installs it on the TV.
Laura: Developer Mode on Samsung is... you press Home, open Apps, type one-two-three-four-five on the remote. If no number keys, press the one-two-three button for on-screen keypad. Switch Developer Mode on, enter your computer's IP, choose OK, restart the TV by holding Power until it cycles.
Sarah: The readme goes deep on the performance tricks. Every animation is a GPU transform or fade. Lists reuse a fixed set of tiles instead of creating new ones as you scroll. The focus ring never moves — the content slides under it. A held-down key can never queue up work: input is applied at most once per frame. Plex resizes every image to exactly the pixels on screen before it's sent. Video goes straight to Samsung's hardware decoder. Only what the TV can't decode — mostly DTS audio — is converted by Plex, and the video itself is never re-encoded.
Laura: The biggest win was one line of CSS. A full-screen CSS gradient behind the UI took almost two seconds to repaint on the TV's CPU. Now the background is a two-by-two-pixel WebGL texture that the GPU stretches to fill the screen: looks the same, costs nothing.
Sarah: WebGL — that's a JavaScript API for rendering 2D and 3D graphics in the browser using the GPU. So instead of the CPU calculating a gradient for every pixel every frame, the GPU just stretches a tiny texture. Massive difference.
Laura: He even built a dev loop. Chrome DevTools can't attach to a retail TV, so dev builds talk to a small server on your computer. You put your computer's host:port in an env file as DEV_HOST, then you get logs, perf samples, remote control. You can curl commands to press buttons on the TV, run JavaScript on the TV from your terminal, replay key sequences for frame stats, A/B test CSS changes live.
Sarah: The code layout is clean: app folder with screens, UI components, Plex API integration, platform abstraction for Tizen keys and AVPlay — that's Samsung's video player API. Scripts for setup and deploy. Tools for dev server, TV eval, network remote. No bundler — the TV's browser runs ES modules natively, and deploy.sh adds modulepreload tags so every module loads in parallel. Cold start about zero point nine seconds versus zero point eight for a minified bundle.
Laura: He ruled out a bunch of things by A/B testing on the actual TV: hero image masks, focus ring shadow, poster fade-ins, row opacity changes, per-tile compositor layers. None made a measurable difference.
Sarah: There's even a section on Plex server quirks. Plex Media Server one point forty-two returns four hundred for start.m3u8 unless a specific transcode decision endpoint was called for the same session first. X-Plex-Platform=Tizen selects the server's built-in profile... the readme cuts off there but you get the idea.
