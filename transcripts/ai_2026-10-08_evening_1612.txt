## Delta-Rule Recurrent State Quantization
Maya: Linear attention models solved the exploding KV cache problem by swapping growing context windows for a fixed-size recurrent state, but it turns out those persistent states are becoming their own kind of memory bottleneck when you are serving concurrent requests.
Leo: That is the exact trade-off we are looking at today, building on some of the edge quantization work we discussed with Qwen3.8-Flash-Next Coder earlier this week. We are diving into a new post-training quantization framework called STEPQuant, published on arXiv, which targets delta-rule recurrent states.
Maya: Walk us through what linear attention actually does with memory, because most people are used to the standard transformer KV cache where memory grows linearly with the sequence length. How does a recurrent state change that footprint?
Leo: In a standard transformer, every time you generate a new token, you append the keys and values of that token to the KV cache. If your context is thirty-two thousand tokens, you store thirty-two thousand key-value vectors for every single attention head across every layer. Linear attention replaces that quadratic growth by rewriting the attention mechanism. Instead of storing past keys and values individually, it collapses them into a fixed-size matrix or vector recurrent state. That state gets updated iteratively at every decoding step.
Maya: So the memory size stays constant whether your context is one thousand tokens or one hundred thousand tokens.
Leo: Exactly. But there is a catch. In high-concurrency serving environments, when you are running models with massive hidden dimensions, those fixed-size recurrent states can still consume gigabytes of memory per request. Naturally, engineers want to quantize them down to four bits or six bits, just like we do with model weights. But if you try to naively quantize a recurrent state using standard uniform quantization, the model's output collapses almost immediately.
Maya: Why does naive quantization break recurrent states so badly compared to static model weights? With weights, they are fixed after training, so you can measure their distribution and quantize them. Why are recurrent states different?
Leo: Because recurrent states are dynamic. They are updated at every single decoding step using a recurrence relation, usually involving a delta rule. When you introduce a tiny quantization error into the state at step one, that error does not just sit there. It gets multiplied, updated, and carried forward into step two, three, four, and so on. Small errors compound over time. By the time you are fifty steps deep, that initial quantization noise has snowballed and corrupted the hidden representation, leading to severe accuracy degradation.
Maya: That brings us to the core discovery in this paper. According to the abstract, the authors found that the impact of these quantization errors depends on two specific dimensions: temporal and spatial. Break down what that means in practice.
Leo: Let us start with the temporal dimension. Not all parts of a recurrent state have the same lifespan. Some components decay quickly, while others act as long-lived memory that persists across many decoding steps. If you introduce a rounding error into a fast-decaying memory slot, its impact washes out pretty quickly. But if you mess up the precision in a long-lived memory slot, that error sticks around and contaminates generations for a long time.
Maya: That makes intuitive sense. It is like rounding a transient intermediate variable versus rounding a core accumulator in a loop. What about the spatial dimension?
Leo: Spatially, errors in different key rows affect model outputs differently. At the same time, the actual magnitudes of the state values vary substantially along both rows and columns. In a delta-rule architecture, the recurrent state is typically a matrix formed by outer products of keys and values, or similar update mechanisms. The authors observed that different rows of the key vectors contribute unequally to the final output error. If you apply a uniform quantization grid across the entire matrix, you end up wasting precious bits on rows that do not matter much, while starving rows that drive critical output activations.
Maya: So instead of treating every element in the recurrent state matrix with equal importance, STEPQuant allocates precision dynamically based on error magnitude and memory lifetime, and it jointly fits key-row and value-column scales. How does that scaling mechanism actually work under the hood?
Leo: The framework looks at the underlying state distributions and explicitly models the impact of each key row on the output error. Instead of just looking at the absolute numerical range of the weights like standard min-max quantization, STEPQuant solves an optimization problem that weights the quantization grid according to how much a given error will actually disturb the model's output. It aligns the quantization bins with the sensitivity of the architecture.
Maya: Let us look at the models they tested this on, because we want to know what kind of hardware and scale we are talking about. What architectures did the authors evaluate?
Leo: They tested STEPQuant on two specific models: Qwen3.8-27B and Kimi-Linear-48B-A3B-Instruct. These are substantial open-weight models that use linear attention or recurrent mechanisms rather than pure standard transformers. They evaluated them across both long-generation and short-generation benchmarks.
Maya: And what did the results show? Did they manage to retain full precision accuracy?
Leo: According to the evaluation in the paper, a six-bit configuration of STEPQuant closely matches the accuracy of the original floating point thirty-two state. And when they pushed it down to a four-bit configuration, it outperformed uniform integer eight quantization. Let that sink in: four bits using STEPQuant beat uniform eight bits, cutting the bit-width in half while delivering better accuracy.
Maya: That is a massive efficiency gain if you are running inference at scale. Did they implement this as a theoretical simulation, or did they actually build systems for it?
Leo: They integrated it directly into SGLang with optimized GPU kernels. By doing that, they achieved over five times recurrent state compression. When you translate that to total serving memory, it reduces memory consumption by up to sixty-eight point seven percent.
Maya: Let us pause on that number because sixty-eight point seven percent total serving memory reduction in a concurrent serving setup is the kind of engineering result that changes deployment economics. Walk through why the total reduction is so high if the recurrent state is only one part of the memory stack.
Leo: In linear attention serving, the recurrent states of concurrent requests pile up fast, especially when you are serving dozens or hundreds of requests in parallel, each maintaining its own state across long contexts. While model weights are shared across requests, the recurrent states are per-request stateful data. As batch sizes and concurrency scale up, the memory consumed by these states starts dominating the GPU memory allocation compared to the static weights. By compressing those states by over five times, you free up massive amounts of VRAM, which directly translates to supporting significantly larger batch sizes or longer concurrent contexts on the same hardware.
Maya: We should be careful about evaluation metrics here. What specific benchmarks did they use to verify that the model did not lose its reasoning or generation capabilities after this aggressive quantization?
Leo: They evaluated across a mix of standard language modeling and generation benchmarks covering both short and long contexts. Because linear attention models are specifically designed to handle long contexts without memory explosion, it was crucial to test whether four-bit or six-bit STEPQuant degraded long-range retrieval or coherence. The paper reports that under the six-bit budget, the performance degradation is practically negligible compared to full-precision FP32 states.
Maya: Are these self-reported numbers from the authors, or have they provided reproducible artifacts?
Leo: The authors released their code on GitHub under the repository name STEPQuant, and the integration is built on top of SGLang, meaning developers can pull the code and inspect the GPU kernels themselves. However, as with any new quantization technique, independent replication across different hardware clusters and a wider variety of downstream tasks will be the true test of how generalizable these spatial-temporal scaling laws are.
Maya: How does this tie back to the broader infrastructure themes we have been tracking this week, like our discussions on edge quantization and memory optimizations in reinforcement learning post-training?
Leo: It highlights a recurring engineering principle. Whether you are looking at LoGRA gradient sketches for training or STEPQuant for inference, naive uniform quantization is hitting a wall. Once you move past static weights into dynamic statesâwhether those are gradients during training or recurrent memory states during inferenceâyou have to account for the internal structure and dynamics of the data. Uniformly squishing numbers into fewer bits ignores how errors propagate through time and space.
Maya: That temporal propagation point is particularly sharp. If an error in a standard weight matrix stays local to that weight, an error in a recurrent state gets fed back into the network on the very next token. Designing a quantization scheme that respects the lifetime of that memory is what separates a model that holds its coherence from one that starts hallucinating gibberish ten tokens later.
Leo: Exactly. And because linear attention architectures are becoming more prevalent as teams search for alternatives to quadratic KV caches for ultra-long context windows, having robust post-training quantization methods for recurrent states is going to be essential for production deployment. Otherwise, you trade one memory bottleneck for another.
Maya: We will keep an eye on how the community adopts the SGLang integration and whether these spatial-temporal quantization principles get extended to other recurrent or state-space models. For now, let us move to our next segment to examine context scaling in robotics.

## Scaling Context in World-Action Models
Maya: Following up on our Wednesday morning look at world action models for robotic control, let us dig into the paper Long-WAM: Scaling the Context of World-Action Models.
Leo: Right, this one addresses a core tension in robotics. Real time robot control needs enough visual history to figure out motion and task progress, but processing all that past video can introduce latency and delay the actual physical action.
Maya: And the paper points out something counterintuitive, which is that having access to history is not the same as actually using it effectively.
Leo: Exactly. According to the paper, longer histories pay off much more when the video foundation model is pretrained autoregressively, meaning it predicts the next token sequentially from left to right.
Maya: How do they handle the training recipe then?
Leo: They use a two-step approach. First, they learn causal prediction from general robot and egocentric videos without any action labels at all. Then, they preserve that history to future structure when they adapt the model for world action tasks.
Maya: What happens when they test that hypothesis?
Leo: They look at RoboCasa GR-1. When they increase the visual context from zero up to nineteen point two seconds, the success rate goes up from sixty three point three percent to seventy eight point seven percent. But interestingly, if they use a bidirectionally pretrained initialization instead, they see no net gain from longer context.
Maya: Because bidirectional models are looking at the whole sequence at once rather than learning a strict causal timeline from past to future?
Leo: Precisely. And they also find that adding robot domain autoregressive pretraining pushes the peak success even higher on both GR-1 and LIBERO-Long. They also report outperforming compared methods on LIBERO-Long, RoboTwin 2.0, and DOMINO.
Maya: Now, let us talk about the production side, because running this on a physical robot is a different beast than running it in a benchmark simulator. How do they keep it from lagging?
Leo: They use streaming observation encoding, asynchronous execution, and hardware specific acceleration to deploy it on target hardware like the RTX 5090, DGX Spark, and Jetson AGX Thor without dropping future video predictions.
Maya: Do they share hard timing numbers for that?
Leo: They do. On an RTX 5090, each action chunk, which includes future video latent prediction, takes one hundred and seven point four milliseconds.
Maya: That is fast enough for smooth physical control. Where did they deploy it for real world testing?
Leo: On Unitree G1 and YAM hardware for dynamic and long horizon manipulation tasks. For instance, they report a ninety five percent success rate on dynamic cup stacking, where baseline models like Pi zero point five and Fast-WAM reportedly succeeded in zero out of twenty trials.
Maya: That is a stark difference in stress testing. Does the paper mention how it fits into a larger robotic stack?
Leo: Yes, as a memory informed executor, it acts as a lower-level controller that can complement higher-level planning in composite tasks, keeping the robot responsive while remembering what it is supposed to be doing.

## Autonomous Agent Workspace Interactions
Maya: On Thursday morning we examined enterprise validation metrics and containerized sandbox isolation on OSWorld-Pro, looking at how agents degrade over long horizons. Today we have new research digging into the mechanics of how autonomous agents actually navigate local files during knowledge work.
Leo: Right, this is a paper titled RunningTab: Direct Workspace Interaction with Environment-Side Tabs, released on October eighth. It analyzes what the authors define as direct workspace interaction, or DWI. In many agent workflows, people rely on retrieval pipelinesâchunking documents, computing embeddings, and building a vector index before the agent can search anything. With direct workspace interaction, you bypass indexing completely. The agent gets dropped into a standard terminal environment and searches the workspace directly using shell utilities like grep, find, and cat.
Maya: Which eliminates indexing latency and infrastructure costs. But if an agent is just dropped into a file tree with terminal commands, why does that interaction pattern break down?
Leo: The breakdown happens in working memory. When an agent is tasked with building a complex deliverableâsay, synthesizing numbers from dozens of spreadsheets, code files, or technical reportsâits context window fills up with raw shell outputs. As the interaction history lengthens, earlier context gets truncated or effectively washed out by newer tokens. The researchers observed two major failure modes. First, the agent runs a directory listing, sees twenty relevant-looking files, opens three of them, and then forgets that the remaining seventeen files even exist. Second, an agent will successfully read a critical figure from a document, but by step forty, when it compiles the final output, that extracted figure has slipped out of active attention, so the deliverable ships without it.
Maya: It loses the thread because it is relying on its own prompt history to remember both the task requirements and what it has or has not inspected. How does RunningTab alter that?
Leo: RunningTab shifts the bookkeeping out of the model's context window and puts it directly into the execution environment. They call this an environment-side tab. You can think of it as a persistent, per-task scratchpad maintained by the sandbox runtime alongside the agent's shell session. At the start of a task, the agent populates the tab with its core requirements. From that point on, whenever the agent executes a command that reads a file, the environment automatically intercepts that action, extracting the text snippet along with its exact provenance, such as the file path.
Maya: What about the files that showed up in a directory search but were never opened?
Leo: The environment tracks those automatically as well. If a terminal command returns a list of file paths, any file that the agent has not yet read gets logged on the tab as an unopened candidate. When the agent checks the tab, it sees a structured view: here is each active requirement, here are the best-matching text excerpts the agent has already gathered, and here are the top unopened candidate files that might address it.
Maya: Does the environment resolve those requirements autonomously, or is the agent still deciding what is finished?
Leo: The agent makes the semantic decisions. It can resolve a requirement by linking it to gathered excerpts, or it can explicitly set a requirement aside if it decides that particular item is irrelevant, provided it supplies a reason. The critical control mechanism is the finish check. If the model attempts to conclude the task and deliver its output while requirements are still open or unresolved, the environment intercepts the termination signal and pushes those unfinished items back to the agent.
Maya: How did this architecture hold up in empirical testing?
Leo: The authors tested RunningTab across three benchmarks using three different frontier language models. They evaluated it against plain direct workspace interaction without tracking, as well as against baselines where the model was prompted to maintain its own internal to-do list in context. RunningTab outperformed the baselines across the board. Furthermore, the researchers measured whether key values needed for the final deliverables were successfully retained on the tab once seen, and found that the environment-side record prevented the information loss typical of long-horizon terminal interactions.
Maya: Though to implement this, your execution environment has to be substantially more complex. You cannot just spin up a standard bash container; the environment needs semantic hooks to parse shell outputs, identify candidate files, and enforce that finish check.
Leo: Exactly. It requires purpose-built environment instrumentation. If an agent operates in an arbitrary, uninstrumented virtual machine, this mechanism cannot function. There is also the dependency on the agent's initial requirement generation; if the model mischaracterizes what the user requested at the start, the tab tracks the wrong targets. But methodologically, it demonstrates that moving task state into external runtime infrastructure is far more reliable than expecting an autoregressive model to maintain its own state over dozens of terminal steps.
